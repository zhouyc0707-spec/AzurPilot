上游在描述文件/提交状态等校验失败时先救援再撤销凭据并清空统计，影响保留历史及回退。用户选择：**保留加密与校验，异常时保留原件和凭据、阻止异常读写，不自动清空。**

已将原清空入口统一改为冻结：先保存 `blocked.json` 阻止读写，再另存救援副本，原数据库、描述与凭据保持；旧 `wiping` 状态不继续清理。冻结跨新对象、进程与服务重启生效。每批读取重新校验状态，已经解封的对象和 CL1 缓存不能绕过冻结。单条密文损坏保留原件，并拒绝覆盖缺失载荷。

### 用户最终决定：备份后删除两条无法解密的旧 CL1 行

升级前数据库有 9 条月度记录，其中 2026-02 和 2026-03 两条仅有旧 `encrypted_blob`，无法用现存设备 ID 解密。已只读检查可用设备 ID 备份，未找到不同旧 ID。当前上游 `opsi_secure.Vault._convert_database()` 遇到无法验证的旧快照会停止全库迁移，影响其它正常数据升级。

曾提供保留密文并隔离对应行、找回旧 ID 后统一迁移、暂缓升级三种方案。用户最终选择直接删除这两条旧记录。执行前额外保存完整删除前数据库，按月份、主键、原始密文和 SHA-256 精确核对；在 SQLite 事务中只删除这两行，9 条变为 7 条，其余记录逐字段一致，删除前后完整性均为 `ok`。原密文继续存在于本机备份中，未删除任何备份。

这是本机一次性清理操作，不在业务代码中添加按月份或异常自动删除的逻辑。两个月的旧 CL1 快照退出活动库，具体内容目前无法解密；其它月份、掉落、资源时间线、经验和汇总文件继续保留。清理后的真实副本已通过完整 V2 迁移与回读验收，解除本次升级阻塞。

读取路径的后台处理改成先同步持久化冻结，再后台保存救援副本；同一批中后续读取和写入立即停止。写事务结束前再次检查冻结标记，即使读取错误被降级为缺失值也不能继续提交。文件锁争用仍作为暂时不可读处理，不冻结、不修改数据。新增测试分别核验链值异常、深检查异常、同批阻断、事务回滚、跨重启冻结和原件及凭据保留。

月度主键修复采用上游自动重建逻辑，但去掉 `INSERT OR REPLACE` 的有损覆盖：记录身份唯一且字段已知时搬运全部历史；存在重复月份、未知字段或已有重建对象时保留原表、明确报错，留待人工决定。当前活动库主键正确，没有此类待决冲突。旧版 `statistics.legacy` 增加与上游相同的页面核对入口，原有卡片、字段、完整黄币/紫币历史和缓存继续保留。
