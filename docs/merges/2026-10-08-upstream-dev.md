### 用户决策的行为冲突：活动商店数量上限

上游会删除 `item:quantity` 后缀并暂停旧任务；本机实际配置保留 18 项数量限制，当前任务关闭。用户明确决定：**保留现有数量上限的兼容支持，合入其余商店改进**。

- 配置迁移保留数量字符串、顺序与启用／关闭状态；不因存在数量后缀关闭任务。
- 具体商品优先于子类／大类，同类货架共享上限，达到配额继续检查下一优先项。
- 仅成功购买后消费并保存余量；失败不扣，零／负上限保持零，不变成无限。
- 全部项目耗尽才沿用原关闭行为；资源余额记录先完成。
- Lua 高级策略的代码与本机脚本均无本地定制差异，本机没有启用高级模式或非空策略脚本；按上游主动撤回同步移除。未来读取实际启用 Lua 的旧配置时仍暂停任务供复核，不静默转换执行。

本轮没有尚未决策的强逻辑冲突。没有重新清理统计原件或凭据，也没有覆盖真实用户配置。

### 合并中发现并修复的问题

1. 上游委托截图清理静态方法误用 `self.config`。在实例保存入口读取运行参数后显式传入，保留默认 50 张、按天数清理优先和备份目录排除；补充回归测试。
2. 可配置岛屿等待与本地静态画面阈值不一致。同步放宽预算并测试长等待和默认值，避免等待未到限就误判卡死。
3. 两处统计测试依赖 Windows 默认编码。CSV 产品代码使用 UTF-8，测试却默认 GBK 读写；仅固定夹具／断言编码并补字节核验，生产解密和数据策略不变。
4. 两处上游迁移测试期待删除数量后缀。按用户已确认的兼容行为更新预期，并覆盖原任务开关、预览和保存；Lua 迁移暂停断言保留。

## 使用与回退

交付合入后，已运行的 Python 服务需要在合适的任务间隙重启服务并刷新浏览器，才会完整加载新后端和页面。前端发布保留旧散列资产，让尚未刷新的页面仍能取得已有资源。

推荐只撤销本次合入、保留后续提交：

```powershell
git -C E:\AzurPilot revert -m 1 <本次合并提交号>
```

本次是双父 merge 提交，`-m 1` 表示以合入前我方分支为主线撤销本次变化。回退后重建前端并重启服务。已有后续工作或真实配置改动应保留；代码回退无需把数据库或配置直接替换为快照，避免丢失交付之后的新记录。确需恢复数据时，应先另存当前数据，再按具体文件核对快照。
